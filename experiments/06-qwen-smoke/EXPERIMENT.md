# Qwen3.5-9B on vLLM: backend smoke test and large-N round timing

## Question

Does `envs/vllm_backend.py` (written and reviewed by reading only) run the swarm agent on Qwen3.5-9B correctly on a
GPU, and what does one synchronous swarm round cost at N=256 and N=1024? This is gate (b) of CLAUDE.md for the
open-weight track (the analogue of the <=$5 Haiku smoke test) and the cost basis for any large-N open-weight design.

## Hypothesis

The backend runs as written except possibly for the two unverified API points (`language_model_only=True` passed to
`vllm.LLM`, and the structured-output import). Beliefs read from digit logprobs have valid mass near 1 (the model
writes a well-formed number after the forced prefix), so fewer than 5% of calls are missing. A round at N=1024 takes
minutes, not hours, on a 48 GB card. Counting against it: missing rate >= 5%, median valid mass < 0.99, or the sampled
prefix not ending in a lone " " token (then the digit path of the module docstring is not the model's natural one).

## Method

Model Qwen/Qwen3.5-9B (bf16, text only), vLLM 0.32.0 (CUDA 12.9 build), prefix caching on, max_model_len 8192,
gpu_memory_utilization 0.90, max_num_seqs 256, max_logprobs 20. The agent is exactly the Claude swarm agent
(`envs/prompts.py`) rendered with Qwen's chat template, thinking disabled, plus the backend's FORMAT_NOTE. Each call:
rationale and public message sampled at temperature 1 under the regex that stops where the number begins; belief =
expected stated probability over the 0.00..1.00 grid from the digit-token logprobs (stage 1: after x, x"0", x"0.";
stage 2: after x"0."d1 for every d1 with conditional probability >= 1e-3); missing when valid mass < 0.95; malformed
samples retried once. `smoke.py` steps, in order:

1. `env`, `tok`: versions, GPU, single-token digits and ".", generation prompt ends in the empty think block.
2. `probes`: 16 single-agent calls per wording (label, inverted): 4 at round 0, 12 at round 1 with a 2+2 inbox of
   fixed realistic messages; every rationale, message, belief and valid mass printed.
3. `swarm`: envs/swarm.py, N=8, K=2, gamma=0, p_neg=0.5, T=4, H=1, two replicas, inverted wording, sync then async
   (same graph and evidence).
4. `timing`: envs/swarm.py synchronous, K=4, gamma=0, p_neg=0.5, T=2, one replica, at N=256 then N=1024; seconds per
   round (sample, stage 1, stage 2 separately) from the backend's `vllm_timings.jsonl`.

## Inputs

Qwen/Qwen3.5-9B from the Hugging Face Hub (Apache-2.0, ungated, 19.3 GB), downloaded on the worker. Evidence and
graphs are generated by the project code from fixed seeds. No data tars.

## Commands

```bash
set -euo pipefail; bash experiments/06-qwen-smoke/setup_vllm.sh
set -euo pipefail; uv run --no-sync pytest -q tests/test_vllm_backend.py tests/test_envs.py
set -euo pipefail; uv run --no-sync python experiments/06-qwen-smoke/smoke.py env tok probes swarm --tag qwen-smoke 2>&1 | tee results/qwen-smoke-steps1-3.log
set -euo pipefail; uv run --no-sync python experiments/06-qwen-smoke/smoke.py timing --tag qwen-smoke 2>&1 | tee results/qwen-smoke-timing.log
```

## Controls

- The unit tests (`tests/test_vllm_backend.py`) pin the logprob arithmetic on hand-made distributions; rerun on the
  worker against the installed vLLM-era numpy.
- `p_sampled` (one draw from the same digit distribution) against `p_logprob`: their mean absolute difference is the
  noise a sampled number would have added, the comparison point for Haiku's stated-number noise.
- Sync against async at N=8 on the same graph and evidence: both must run; their dynamics are not compared here.

## Success and failure criteria

- Supported (backend usable as is): all steps complete, missing rate < 5% over all calls, median valid mass >= 0.99,
  the sampled prefix ends in a lone " " token in all probes, timing recorded at both N.
- Not supported: steps complete but missing rate >= 5% or median valid mass < 0.99 (the belief readout needs work
  before calibration).
- Failed run: vLLM won't install or load the model, or a step errors in a way not fixed within this run.

## Time and cost

Setup about 15 minutes (uv sync, vLLM install, 19 GB model download), engine start about 3 minutes, steps 1-3 about
10 minutes (the async swarm is 64 sequential calls), timing unknown: that is what this run measures; the estimate
is 1-5 minutes per round at N=1024 on an A40. Expected total under 1 hour, about $0.60 on an A40 ($0.59/hr). Cap 2 h;
budget $5 lets the A100 ($2.19/hr) serve as the last fallback. Memory: one process; weights 19.3 GB (text only)
leave about 20 GB of the 48 GB card for KV and linear-attention state at utilization 0.90. CPU use is light (one
Python process plus vLLM's workers). If the N=1024 timing would exceed 30 minutes per round, stop after one round
of it and report the partial number.

## If something fails

- `language_model_only` rejected by `vllm.LLM`: replace it in `make_llm` with `limit_mm_per_prompt={"image": 0,
  "video": 0}`, push, rerun; record as an amendment.
- Structured-output import or parameter error: fix `_vllm_params` to the installed API, push, rerun.
- Out of memory at engine start: lower `max_num_seqs` to 128, then `gpu_memory_utilization` to 0.85.
- Prefix caching unsupported for this hybrid model: rerun with `--prefix-caching 0` and record it (timing then
  includes recomputing the shared prefix four or more times per call).
- Any other error: read the traceback, fix within the backend if it's a bug in it, otherwise stop and report.
Every call is checkpointed as it finishes (`vllm_calls.jsonl`), so a stop at an arbitrary moment loses at most the
current engine batch, and a rerun replays the finished calls.

## Fixed rules

- The missing rule (valid mass < 0.95, one retry for malformed samples) is not loosened during the run.
- No belief is ever parsed from text.
